# 项目展示与简历描述

展示项目：**研证｜证据驱动的 AI 科研工作台**

仓库：<https://github.com/mingxuanyan07-lgtm/yanzheng-research-workbench>

类型：个人项目，使用 AI 辅助开发。应用版本：0.5.0。

## 可用于简历的版本

**研证｜AI 科研工作台** · Python / FastAPI / SQLite / JavaScript / Qwen

- 构建从研究问题澄清、文献导入、候选修订到人工选题与验证记录的完整工作流；通过结构校验、上下文指纹和待审提议，防止模型建议直接覆盖研究者决定。
- 实现 PDF/TXT/MD 原文导入、Unicode 摘录定位与引用回跳，将候选判断关联到阅读笔记和证据快照；来源或笔记变化后保留旧关联并要求重新核对。
- 采用 SQLite 事务持久化项目与原件，提供完整性校验、原子恢复及重复导入保护；整理两份真实公开论文案例，保留原文位置、9次真实模型调用和人工取舍，交付三分钟演示。

以上描述陈述仓库中的工程能力。应根据自己能够解释与维护的内容选择条目，并如实说明 AI 辅助开发过程；不应将辅助生成的代码或建议包装为已验证的科研成果。

## 可以展开讲的工程问题

| 问题 | 对应实现与取舍 |
| --- | --- |
| 为什么不直接把模型输出作为当前研究结果？ | 待审提议、来源/笔记校验、明确接受/拒绝和历史版本；模型接口成功不等于科研判断正确。 |
| 如何处理笔记或问题改变后的旧建议？ | 保存生成上下文和证据快照，过期提议不能直接接受；既有内容作为历史保留。 |
| 如何证明引用真的指向保存的那段文字？ | 文档归属、页码、Unicode 字符范围、原句与 SHA256 联合检查；只证明字节和定位一致，不认证论文结论。 |
| 为什么用 SQLite？ | 单人同源应用部署简单；写事务保持短，网络与实验执行在事务外；恢复先校验、再原子写入。 |
| 如何避免演示结果与真实结果混淆？ | 合成验收、预置样例、实际请求、固定实验和人工决定分别留存来源及状态。 |

## 不应写入简历的说法

- 未测量的“效率提升 XX%”“准确率 XX%”、用户量、导师采用率或规模化生产指标。
- 将可选的固定 Lean 案例描述为“自动证明任意数学命题”。
- 将6组冒烟检查描述为已经完成正式90组实验，或已经提出了新的随机 SVD 算法。
- 将两份公开论文操作案例描述为独立用户试用或真实科研成果。

固定 Lean 的间歇超时、多用户生产化、OCR 与独立用户效果评估仍是后续工作，详见 [路线图](ROADMAP.md) 和 [历史验证记录](validation-github-sync-2026-10-25.json)。
